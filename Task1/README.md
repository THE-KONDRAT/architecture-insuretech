# Соображения при разработке архитектуры

## Масштабирование
Использование вертикального масштабирования ограничено, и не покроет пиковые периоды. В тексте задания сказано, что предполагается значительный рост количества пользователей и запросов, но не сказано, что это будет непостоянная нагрузка, поэтому я предполагаю, что резких пиков, значительно превышающих среднюю нагрузку, не будет: рост нагрузки от рекламной кампании плавный и покрывается HPA.
Исходя из этого не вижу смысл использовать CA масштабирование. Поэтому в качестве механизма масштабирования выбран Horizontal Pod Autoscaler.
Для масштабирования используются метрики утилизации CPU и Memory.
Минимальное количество реплик на сервис – 2 для повышения отказоустойчивости.

## Высокая доступность
Для снижения сетевой связанности будут использованы раздельные кластеры Kubernetes, а не один геораспределённый.
Ограничение скорости запросов осуществляется по алгоритму Token Bucket. Это позволит обработать резкие всплески активности, как было с одним из клиентов.
Failover-стратегия используется как Active-Active, в том числе из-за необходимости обеспечения высокого значения доступности.

Известно, что объём данных 50Гб, но структура данных на текущий момент не известна. На текущий момент смысл шардирования не столь очевиден, можно для некоторых сервисов с целью уменьшения количества синхронных взаимодействий держать локально подготовленные необходимые данные.
При росте нагрузки и выявлении проблемных данных можно будет задуматься о шардировании.
Для повышения отказоустойчивости создаются реплики PostgreSQL в обеих зонах доступности. Автоматический failover осуществляется с помощью Patroni, etcd и HaProxy. При потере Primary ноды HaProxy бесшовно переключает соединения на резерв.
Для обеспечения сохранности данных используется PITR: непрерывный WAL-архив и периодические base backup, которые выгружаются в Object Storage вне зон доступности. RPO стремится к 0 за счёт синхронной репликации, что укладывается в требование 15 мин. RTO тоже с запасом укладывается в 45 минут за счёт автоматического failover Patroni.

##  Быстродействие
Для обеспечения одинакового времени загрузки из регионов используется CDN, хранящий статические ресурсы и проксирующий запросы к API.
