# Проектирование продажи ОСАГО


## Обработка заявки
Контрагенты предоставляют идентичный API с двумя методами, таким образом при получении запроса от клиента в систему контрагента совершается запрос на создание заявки ОСАГО, далее в течение таймаута (60с - максимальное время ожидания решения от страховой) с определённой периодичностью (2-5 секунд) производятся запросы получения предложения по заявке, которые прекращаются в тот момент, когда ответ будет дан.

## Хранение и интеграция
Сервису osago-aggregator требуется своё хранилище данных, чтобы не терять информацию при падении.
При публикации событий в очередь используется transactional outbox в БД osago-aggregator. Идемпотентность обеспечивается на стороне потребителя по eventId.
Сервис предоставляет core-app один метод для создания заявки, а дальше решение публикуется в топик kafka `osago-offers` (события `offer.received` или `offer.timeout`).
Запрос от core-app к osago-aggregator синхронный (REST API, POST /osago-requests), запрос возвращает id заявки.
Web-приложение взаимодействует по SSE с core-app (например, GET /osago-requests/{id}/events). core-app получает результат через подписку на топик kafka (и публикует предложение через SSE).

## Отказоустойчивость
Для обращения к страховой можно применить механизм retry с числом попыток 3. Timeout каждого вызова страховой 5с ограничивает общее время удержания слота обработки заявки.
При ошибке сначала повторная попытка запроса предпринимается через 2 секунды, далее через 4 и потом через 8с. Общий дедлайн 60 с, из-за этого число попыток ограничено. По истечении дедлайна или превышении числа попыток публикуется событие `offer.timeout`. Клиенту показываются только предложения от ответивших страховых компаний.
Допустимое время ожидания со стороны клиента нужно уточнить у аналитиков, но на текущий момент стоит ориентироваться на те же 60 секунд.

Между core-app и osago-aggregator стоит сделать circuit breaker, так как это заранее проинформирует клиентов о неработоспособности сервиса, обеспечивающего функционал, и уменьшит бесполезные висящие запросы.
Дедлайн в 60 секунд ограничивает число заявок, которые один инстанс сервиса обрабатывает одновременно, поэтому хоть Circuit Breaker на вызовах к страховым компаниям и позволит досрочно прервать запрос, на первом этапе можно обойтись дедлайном, и внедрить Circuit Breaker только по мере необходимости.

Rate Limiter стоит сделать в следующих местах:
- На общем API Gateway (Token Bucket, ограничит запросы от пользователей и партнёров B2B отдельной квотой)
- В osago-aggregator ограничение числа запросов осуществляется на основе ёмкости: при исчерпании слотов параллельных опросов новые заявки отклоняются быстрой ошибкой (механизм backpressure), вместо перегрузки и массового нарушения дедлайнов. 

## Нюансы запуска множества экземпляров
- Kafka. Так как необходимо, чтобы все экземпляры core-app читали все события (чтобы на своей стороне отфильтровать те, которые относятся к их заявкам), нужно, чтобы каждый экземпляр был в своей consumer-group, чтобы сообщения не делились между инстансами, а все попадали на каждый. Минус – увеличение нагрузки на Kafka и сеть.
- Так как SSE должны быть привязаны к конкретному pod-у, то Load Balancer необходимо настроить на режим Sticky Session.
  - graceful shutdown корректно закрывает SSE-соединения
  - Если pod перезапускается, то клиент переподключается на другой инстанс.
