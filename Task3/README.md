# Проблемы текущего решения
1. Циклы опроса сервиса (синхронное взаимодействие) вместо потребления событий.

    Здесь есть две проблемы:
    
   1. Регулярный синхронный сервисный трафик core-app → ins-product-aggregator
   2. Тяжёлый запрос раз в сутки к core-app → ins-comp-settlement
   3. Также возможны проблемы с запросом всех оформленных ставок (ins-comp-settlement → core-app)
2. Хрупкая цепочка запросов

    Аггрегатор отправляет синхронные запросы в 5 страховых, в это время к нему висит запрос от core-app. Задержка от любой компании создаёт вероятность падения всей цепочки по таймауту.
    Увеличение числа контрагентов увеличит вероятность сбоя цепочки, что потребует либо увеличения таймаута (то есть большей сетевой нагрузке), либо пересмотра типа взаимодействия

3. Связанность сервисов к расписанию и доступности друг друга
   
    Обновления привязаны к расписанию и зависят от доступности аггрегатора и core-app.

4. Ночное обновление

    Реестр собирается одним тяжёлым запросом, который при росте числа обновлений может стать очень тяжёлым, и может не уложиться в окно. Также нет гарантии доставки: при недоступности core-app реестр оформленных страховок может не сформироваться.
    
    В задании ничего не сказано про ретраи, поэтому предполагаю, что в случае сбоя обновления данных просто не происходит, что утяжеляет следующий цикл обновления.

## Предлагаемое решение
1. Заменить регулярные опросы на получение событий (взаимодействие core-app → ins-product-aggregator)
2. Разбить цепочку опросов на части: ins-product-aggregator в своём темпе опрашивает API страховых компаний (при этом таймауты могут подбираться индивидуально, а ошибки при взаимодействии также решаться с контрагентом индивидуально, сбой API одной компании не блокирует остальные), затем он агрегирует изменения и публикует события в топик, откуда core-app и ins-comp-settlement потребляют эти события в удобном им темпе
   1. Создать собственную БД для сервиса ins-product-aggregator, это необходимо для публикации изменений (diff). Также там будет находиться outbox-таблица.
3. Заменить запрос для получения всех оформленных ставок за день на потребление событий по оформлению ставок (взаимодействие ins-comp-settlement → core-app)

Для асинхронного взаимодействия предлагаю использовать топики, так как это даст возможность подключать новые сервисы к ним. Хотя на текущий момент и известно, какие сервисы будут потреблять события, от использования очередей лучше уйти сразу для расширяемости.
Перед публикацией события в топик сервисы должны использовать паттерн Transactional Outbox для исключения потери события при сбое сервиса в момент публикации. При этом обрабатывать outbox следует в том же процессе (периодический polling). CDC-решение типа Debezium не используется намеренно: оно требует дополнительной инфраструктуры (Kafka Connect, коннекторы), а при текущих объёмах (50 GB, события о тарифах и оформлениях) in-process relay проще и достаточен.

Для обеспечения идемпотентности необходимо вести лог обработанных событий, а в событие добавлять уникальный идентификатор. Если по событиям нужно будет делать запросы по времени, то стоит выбрать UUID v7, в противном случае достаточно UUID v4.
В качестве брокера сообщений используется Apache Kafka: топики с consumer-группами предоставляют события на оба сервиса-потребителя, а лог событий позволяет новым потребителям прочитать историю с начала и догнать пропущенные события после простоя.
